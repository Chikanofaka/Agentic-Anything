## Findings and repairs

### Voice capture and manual recovery

Confirmed in code: the voice draft was read-only throughout capture; its final text could remain empty while partial recognition was displayed separately. A stalled recognizer could leave the UI indefinitely reporting “Listening,” with no editable fallback.

Likely native cause: a recognition task was started during interviewer playback while its audio frames were intentionally gated for echo resistance. Reusing that task after natural playback completion or barge-in could leave it starved or already ended. This is a code-supported failure mechanism; the supplied screenshots do not prove the acoustic cause of the reported run.

Repairs in `native/Voice.swift` and `ui/voice.js`:

- During playback, the echo-resistant onset detector remains active; a fresh recognition task starts on candidate barge-in or normal playback completion. Bounded candidate preroll preserves the beginning of an interruption, while natural completion discards playback frames.
- After detected candidate activity, eight seconds without nonempty transcription pauses capture with `VOICE_RECOGNITION_STALLED`. It preserves the automatic-send preference and provides a recovery route without a model request or automatic paid retry. Ordinary silence does not trigger this failure.
- Partial transcription now appears in the draft. **Edit draft**, or intentional focus in the draft, pauses capture, preserves the latest text and invalidates late recognition callbacks before manual editing.
- Automatic sending still requires at least five uninterrupted seconds of actual candidate silence. Recognizer finalization alone cannot send. Pausing capture does not pause the interview clock. Faster playback, the minimized companion and new-question automatic-send defaults remain.

### Evaluator citation failures

The reported first/second-question errors rejected proposals with inadmissible evidence references. More conversation is not itself an error, and successful evaluation of the shorter third question does not establish correctness of the other requests. Preserve rejection guards rather than accepting uncited or cross-question claims.

The new `tia-evaluator-structured/v2` response contract gives each of **T01–T05 and C01–C06** its own object containing `anchor`, `evidence` and `reason`. Each criterion's evidence enumeration comes from its authorized candidate-event aliases. An unavailable criterion must return a null anchor and an empty evidence list. Native parsing revalidates the object before the existing Host evidence and arithmetic checks.

The full chronological conversation remains the context for the new continuity policy. Capacity errors remain explicit; there is no silent truncation or replacement turn cap. SQL correctness requires the separate verified-execution evidence. A Finish action is still not evidence of closing-speech quality. Legacy response contracts and archived proposals retain their historical interpretation.

### Recorded communication practice points

`tia-recorded-communication/v1` adds a separate, deterministic practice observation for an eligible completed record containing only code submissions or bare requests for help: **0/40 recorded communication demonstration points**. It does not claim zero communication ability or overwrite an evaluator proposal. Clarification, planning, explanation or a reasoned assistance request still requires semantic review; action labels alone do not establish quality.

This is not a general conversion of every null to zero. Explicit capture failure, incomplete/absent records, skipped or timed-out opportunities, and legacy policies retain their distinct unknown/inapplicable states. Recording health is not attested merely because no error event exists. In particular, this UAT's reported voice failure means an empty transcript cannot establish that the candidate never attempted to communicate. All 11 rubric dimensions remain available; missing SQL evidence is not a communication zero.

### Post-interview SQL examination

The completion page now offers a separate local execution workflow for the latest saved SQL submission:

1. Select the matching reviewed suite and inspect its assumptions, synthetic inputs and expected outputs.
2. Confirm that the suite matches the question, then authorize **Run reviewed cases · no AI request** through Native.
3. Inspect the per-case execution statuses and source hashes. Only a committed result bound to the exact question, submission and reviewed suite can supply new execution evidence.

Three finite suites cover immediate first deliveries, monthly transaction aggregates and the last passenger within a 1000 kg bus limit. Each contains three curated cases. These are local regression cases, not official hidden tests or proof of exhaustive edge-case coverage. PostgreSQL and an eligible saved submission are required; Pandas, an unavailable backend or missing SQL cannot be represented as a passing result. A model's reasoning or proposed reference answer is not execution.

Execution runs asynchronously through the Native/local worker boundary, with cancellation and stale-result checks. It adds retrospective observations without rewriting the timed interview. Prior evaluator proposals are archived when their context changes. Requesting another model evaluation remains a separate paid-consent action; local testing never triggers it automatically. Private reference answers remain sealed.
