**建议的实现边界 [ENGINEERING PROPOSAL]**

采用一个受审查的 interview domain binding，加一个面试专用 session/controller 与本地文本 UI。复用 HAL 的包检查、固定可信注册方式、类型检查及经过核验的持久化能力；不要把 Witness 的状态字段、快照、轮数、提示规则、模型请求上限或话术直接复制为产品规则。先做无模型、无网络的人工/脚本情景适配器，明确标为 SIMULATED；技术测试可以是真实执行，语义质量判断仍须标注人工或模拟来源。

答案、隐藏测试与裁判资料放在控制器私有侧；给候选人的视图由白名单投影生成。审计发现既有 Witness `snapshot()` 含完整 state，因此新面试不能依赖其 `public_view` 自动保密。一个本地应用不能阻止设备所有者自行读取自己的安装文件；这里的保密目标是应用、角色和模型上下文不主动越权泄露，并明确区分本机所有者威胁与进程隔离威胁。

**MVP 的 P0 Communication 交付定义 [SOURCE + ENGINEERING PROPOSAL]**

每阶段都定义“观察机会 → 候选人原话/产物 → 质量判断 → 后续行动证据”，不能用一段总结代替。候选人说明已完成内容、已验证内容、具体缺口、独立提出的下一步、政策允许的精确求助，以及收到回复后的行动；并非每轮强迫说齐六句话。无求助机会时记不适用；尚未观察时记缺证据，而不是自动低分。

| 阶段 | Communication 独立证据 | 与 Technical 的边界 |
|---|---|---|
| 开场/规则/澄清 | 确认限制、复述目标、提出消歧问题 | 规则复述清楚不等于解法正确 |
| 计划/权衡 | 说明路线、假设、阶段预期及取舍 | 技术可行性和复杂度由 Technical 判断 |
| 编码/执行 | 有意义的阶段进展与下一步说明 | 代码执行和测试结果独立记录 |
| 卡住/求助 | 已知事实、未证实假设、精确缺口和合规请求 | 缺语法与缺结构知识分别标记 |
| 收到反馈 | 准确解释反馈、说明改变以及后续行为 | “明白了”不能自动生成执行或通过证据 |
| 被拒/再卡住 | 接受边界、说明替代路线或合理终止 | 不以获得提示本身奖励沟通能力 |
| 测试/修复 | 区分通过与失败的范围，解释最小修正假设 | 测试通过数量不直接等于完成百分比 |
| 收尾/复盘 | 陈述已验证结果、局限、下一步与帮助归因 | 礼貌或自信不能替代正确性；不强求人格表演 |

**可增量验收的工作包 [ENGINEERING PROPOSAL]**

下列估算是一个熟悉代码的工程师的有效工作日区间，不含用户评审等待、真实模型校准或外部研究；没有把这些估算视为已验证工期。

| 包 | 模块与产出 | 依赖 | 完成判据 | 估算 / 主要风险 |
|---|---|---|---|---|
| WP0 | 来源清单、版本哈希、需求映射、冲突表 | 当前资料 | 所有 P0 可追溯；缺失评审项不伪造；原 Atlas 保持原样 | 0.5–1 日；评审材料不完整 |
| WP1 | 版本化 graph-policy.json + 变更提案 | WP0 | B05 已批准修正；每边有条件/角色/动作/终止；理解、实施、进展独立 | 1–2 日；Atlas 是评审草案，不是可执行规格 |
| WP2 | Session/controller、事件账本、私有/公开投影 | WP1 最小切片 | 序号由宿主生成；重复提交不重复计数；恢复保持版本；答案不进入候选人视图 | 2–3 日；旧 host 与 Witness 耦合 |
| WP3 | 面试官动作与候选人再决策、人工/情景适配器 | WP2 | 两轮以上完整循环；沉默、追问、有限提示、拒绝、到时都可回放 | 1.5–2.5 日；不能把沉默推断为失败 |
| WP4 | 一个可执行 SQL 题包、受限执行器、测试 oracle | WP2 | 已知输入输出可验证；保留部分成果；小错误与结构错误有不同 fixture；时间/资源/权限受限 | 2–4 日；仅 SELECT 字符串过滤不构成安全沙箱 |
| WP5 | 全阶段 Communication observation + assessor 接口 | WP1、WP2；可与 WP3/4 并行 | 每阶段独立证据；区分 observed/missing/N/A/insufficient；精确原话及行动关联 | 2–3 日；语义判断不能冒称确定性事实 |
| WP6 | 双评分、独立 bonus、可解释 review | WP4、WP5 | 固定技术证据更改沟通质量仅影响 Communication；反向同理；权重/方法/置信/来源可见 | 1–2 日；缺证据处理和子维度权重未冻结 |
| WP7 | Trainer handoff、针对性 drill、第二会话比较 | WP6 | 只读已关闭会话；练习目标引用具体证据；无证据时不声称进步 | 1–2 日；同题记忆不能证明迁移 |
| WP8 | 本地文本 UI + 时间线 + 证据复盘 | WP2、WP3、WP6、WP7 | 开始→对话→提交→结束→双评分→训练→第二会话；每个模拟步骤清楚标注 | 2–3 日；UI 不应拥有时间/测试/分数真值 |
| WP9 | HAL curated binding 接入与回归、安全验收 | WP2 首个契约 spike；完整验收在 WP4–8 后 | 新域显式注册；现有 HAL/Witness 回归不退化；私有资料和多角色权限负测通过 | 1.5–3 日；共用接口变更范围扩大 |
| WP10 | 对抗场景、回放、验收回执、人工评审 | WP3–9 | 执行验收矩阵；分别记录 PASS/FAIL/NOT_RUN；未经确认的规则保持提案 | 1–2 日；测试正确不等于训练效果有效 |

总工作量粗估 15.5–27.5 人日；多线并行可以缩短日历时间，不能把工作量简单除以代理数量。最先验证的技术风险是 WP2/WP9 的权限和持久化接口，以及 WP4 的执行隔离。它们通过前先使用可信预计算 fixture 演练流程，不接收任意代码。

**建议的三个可审阅里程碑**

1. M0：本文、本次来源映射、架构评估、测试矩阵、规则来源登记。范围是工程发现和原型设计。
2. M1：无需 API 的本地合成情景闭环，至少走通独立完成、第二次卡住、被拒求助、结构性修复、到时结束；双评分和 Trainer 交接可回放。这只证明流程与接口，不证明自然语言理解或市场有效性。
3. M2：一个真实受限 SQL 执行题、人工评估证据与第二场可比练习接通；通过新增域负测和旧域回归后，再评审是否接真实模型。费用、provider、隐私、预算及 live UAT 另行明确。

**评分与配置的实现约束 [SOURCE]**

当前 Rapid PRD 的 Plan 1 是 Technical 60、Communication 40，独立显示基础分；可选正向 bonus 上限 +10 单列。它是本次产品试行方案，不是雇主标准。Technical 包含计划、概念、实现、测试、修复与边界预见；约 20% 的 technical 边界预见子权重仍是候选建议，不形成第三大类。旧 PRD 的 40/20/25/15 或 Atlas 历史权重不进入默认计算。

每条规则保存 `rule_id, value, status, source_ref, source_version, graph_refs, issue_refs, rationale, validation_state, effective_from, supersedes`。提示层级、次数、时间、帮助触发条件、子维度权重、bonus 锚点、停滞判定、缺证据计算都可配置；未知值保持未设定，启动相应评估前要求完整 profile 或选择明确标注的实验配置。不因技术通过率变化自动修正 Communication，也不因沟通流畅改变技术测试结果。允许同一事件分别支撑两个有不同理由的判断，但各自保留证据和方法，不把一次印象复制为两份分数。

来源状态与验证状态分开：用户提出一个规则不等于它已经通过效果验证；工程上验证了计算正确也不等于验证了权重合理。新规则采用版本化 proposal 与人工接受动作，不能自动改写已完成场次。安全执行边界不允许被用户文本或模型建议关闭。
