Extract only the genuinely shared storage/transport pieces when the second controller demonstrates the needed interface. A generic plugin platform rewrite is unnecessary for this MVP.

## 5. New modules needed for the interview loop

All items below are **[ENGINEERING PROPOSAL]**, scoped by current Rapid PRD FR01–FR10 rather than inherited HAL product behavior.

1. **Question package and runner:** public prompt/schema/sample data; separate evaluator fixtures and permitted hint fragments; pinned question/test versions. Implement one SQL dialect with explicit row-order, duplicate, NULL and numeric-comparison rules. Run a restricted read-only query in a disposable bounded worker: no extension loading, file/database attachment or arbitrary Python; an allowlisted SQL authorizer, execution limits, result-size limits and parent timeout must be tested. Read-only syntax or a Python subprocess by itself is not an OS sandbox. Use a fixed synthetic database and no personal data. If these execution controls are unproved, label the slice as a fixture simulation and leave arbitrary candidate execution unavailable.
2. **Session/policy controller:** source-mapped states and decisions; corrected B05; explicit aid policy and scoped hint grants; syntax versus structural diagnosis; actual feedback-to-action progress; repeated blockage; silence/probe/decline/close options. Host owns deadlines and expiration checks before/after work. Define restart, pause, and late test-result handling explicitly. Do not encode “80% solved” or “4/20 passes” as help eligibility or failure severity.
3. **Evidence ledger and immutable closed report:** host-assigned event sequence/IDs; candidate text and code versions; trusted test receipts; selected action and allowed disclosure; assistance history; source/graph/policy/rubric versions. A state reducer should replay the same committed evidence under the recorded version. Revised assessments append a new version instead of rewriting what was observed.
4. **Separate assessment functions:** deterministic test/score arithmetic plus auditable judgment records; Technical and Communication assessed independently. Model-generated judgments, if later enabled, remain proposed assessments with evidence references and confidence, not new facts.
5. **Trainer handoff and comparison:** consume the closed committed report, choose a traceable gap/drill/success measure, then prepare a new interview without leaking its answer. Compare matching conditions and rubric versions; distinguish a repeated question from transfer to an unseen one. A second-session score increase alone does not establish generalized improvement.
6. **Specialist UI:** one environment for rules/timer, prompt, dialogue, SQL/artifact editing, permitted test output, submission, post-close evidence/score and drill. The teacher/Trainer view opens only after close. The UI sends bounded commands to its controller. An isolated static demonstration may help review, but it is not the full authoritative runtime or proof of protected answers. Native private-pipe transport is a later narrow adaptation; an HTTP implementation would need its own authenticated local boundary and is not inherited from this code.

## 6. Communication is independent evidence, not inferred from passing SQL

**[SOURCE / CURRENT PLAN 1]** Rapid PRD lines 17–18, FR05–FR06, and lines 58–61 require a separate Communication process and score, with base **Technical 60 + Communication 40**, optional positive **bonus up to 10**, and explicit observability/quality/confidence. These are the current product's illustrative weights, **not empirically verified employer scoring rules**. Edge-case foresight remains inside Technical. Internal subweights and missing-evidence aggregation require explicit versioned proposals; no hidden normalization to a perfect score.

**[ENGINEERING PROPOSAL]** Each assessment record should contain dimension, phase, observable opportunity, evidence IDs/spans, presence/applicability status, quality rating, confidence, assessor/method, assistance condition, and explanation. Use `not_observed`, `not_applicable`, and `insufficient_evidence` distinctly; a missing observation must not be silently rewritten as a failed behavior.

| Phase | Communication evidence | Separate technical evidence |
|---|---|---|
| Clarify | Accurate restatement and focused questions | Requirement interpretation and chosen result semantics |
| Plan | Concise staged explanation, assumptions and trade-offs | Plan feasibility and conceptual correctness |
| Implement | Progress update explains purpose, completed work and next step | Versioned code/query and intermediate outputs |
| Stuck/request help | What is done/proven, exact gap/risk, independently proposed next step, permitted precise request | Diagnosis accuracy, local versus structural gap, scope of assistance |
| Feedback/retry | Correctly explains feedback and communicates what changed | A changed artifact and observed test/action outcome; “aha” alone is not progress |
| Partial/full result | Honest account of validated and unvalidated parts | Per-case outcomes and coherent remaining subproblem |
| Close | Clear recap, limits, trade-offs and next work | Final submitted artifact and completion scope |

The same event may support different assessments, but neither dimension substitutes for the other. A passing query does not prove clear communication; a clear failure diagnosis does not make a failing query correct. Observe constructive recovery for the separate optional bonus without deriving personality, charisma or emotional state from wording. Give Trainer the specific missed behavior and its evidence, not merely a combined low score.

**[ENGINEERING PROPOSAL] Deterministic versus judgment boundary:** host timestamps, recorded actions, authorized hint disclosures, pinned test outcomes and aggregation can be reproducible facts. Semantic reasoning quality, communication quality, valid unfamiliar approaches and general complexity claims require evidence-based assessment. Requiring structured explanations makes evidence inspectable; it does not make candidate self-report true. Scripted/keyword fixture classifications must be labelled as such and cannot be reported as validated natural-language assessment.

## 8. Remaining decisions and feasibility limits

**[ENGINEERING PROPOSAL] Nonblocking working choices:** local text-first, one synthetic SQL challenge, deterministic scripted interviewer responses for the first acceptance slice, explicit manual/fixture assessment where semantic quality is not yet validated, no provider invocation, curated host adapter only. These choices permit useful safe work now and are not claims about the most common UK interview format.

**[RESEARCH PENDING]** Realistic employer help policies, representative question difficulty, appropriate internal scoring weights, reliable rubric calibration/inter-rater agreement, natural-language classification quality, and transfer to unseen interviews require research/UAT. The current architecture does not resolve them.

**[ENGINEERING PROPOSAL] Before executable MVP acceptance:** prove SQL containment and resource bounds; settle clock/restart semantics; decide evidence retention/export/deletion and assessment revision behavior; implement separate context projections and the closed-report handoff; select and verify the UI-to-controller transport. Later live model access needs its own consent, cost/privacy design and capability tests. No such external action is necessary for the isolated offline slice.

**Readiness classification:** architecture discovery is supported by actual code and fresh baseline tests. A narrow curated integration is feasible with additional modules and tests. Generic Type B activation, interview intelligence, validated scoring, secure arbitrary-code execution, live provider behavior, and market effectiveness remain unproved.
